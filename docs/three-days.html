day 1

The model runs in the repo now

Everything in RT started from a label raster somebody else produced. segmap segment is the step before that.

RGB ortho in, single-band wire-id GeoTIFF out. The fixed models emit one class index per pixel, not a class-probability stack — preds is int64 (1, H, W) and the integer is a sparse product wire id in 0..241, the same id space RT already reads. So there is no argmax to take and no channel bookkeeping to get wrong: preds goes to disk verbatim and loader translates it exactly as it does a tile that arrived from the product. roads and dsem_landcover come free in the same forward pass and are dropped — nothing in RT consumes either.

Three guards, because this failure mode is silent

A segmenter run wrong does not crash. It returns a plausible map of ground that is not there, and nothing downstream can detect it. So:

guardwhat it stops
scaleone model per resolution, chosen from the raster's own m/px by ratio — 0.3 m is 2.4× the 12.5 cm model and 0.6× the 50 cm one, so the second is the less wrong. Warned past 5% off native, refused past 25%, and the warning prints before the inference, not after 35 minutes of it.
seams--tile 1024 --halo 128 feeds the network 1280² and keeps the middle 1024². One fixed input shape for every tile, edge tiles included — so no tile boundary prints itself into the map.
8-bitthe producer's normalisation is (v − ImageNet mean) / std, which means nothing on 16-bit imagery. Refused, not scaled on a guess.

The weights arrived named ST_15cm_model.onnx, which they are not: byte-identical (md5 88ba82f8…) to the product's Merged_2025-02-13… release, whose own registry calls it RESOLUTION_12_5. Renamed to ST_12_5cm_model.onnx; LEGACY_NAMES keeps the old name resolving so nobody else's models/ directory breaks.

how it is tested

36 tests, driven by a stub session whose “prediction” is a known function of its input — so segment_array(rgb) must reproduce rgb[...,0] exactly. That is what catches the four things which can actually go wrong here: a seam, an overlap, an interior taken at the wrong offset, or the bands reversed. A real forward pass catches none of them, because a plausible map of the wrong ground looks exactly like a plausible map. One test uses the real weights and asserts every id the model can emit has a name in the bundled mapping; it skips when they are absent.

the result

What the two dates record

33.107 N, 35.239 E — southern Lebanon, 2.113 × 1.024 km, 216.5 ha. Per the project owner the interval between the two acquisitions contains the Israel–Lebanon war, and buildings on this ground were destroyed.

a unit warning that applies to every figure below

The rasters are EPSG:3857, whose unit is a pseudo-metre: at 33.1 N one unit is cos(φ) = 0.838 true ground metres. RT takes the header at face value, so every area it prints on this AOI is 42.5% too large — it calls this ground 308.5 ha when it is 216.5. Every hectare on this page is true ground, converted. The defect itself is register item 2.13, found by the review below.

The structures

And the rubble is where the buildings were

the damage inventory, and why it is a floor

House → Clutter covers 3.39 ha over 2,579 components, of which 220 clear a 20 m² floor and hold 91% of the area. My first instinct was that 220 undercounts because one building fragments into several patches. Wrong — the reviewer measured 1.09 patches per building.

It undercounts for two worse reasons. Burning the cached OSM snapshot gives 2.08 mapped buildings per House component — adjacent buildings share walls and merge under 8-connectivity. And of a random 12 OSM buildings this metric scores as undamaged, 12 were destroyed in the imagery: 20% of building footprints read as bedrock in 2025, not as Clutter. 220 is low by roughly 2–4×, and the defensible statement is that essentially the whole building stock here is destroyed or heavily damaged.

correction

Three things I reported wrongly

Two of them on the same finding, in opposite directions. They belong on this page for the same reason the rest of it does.

1 · “These are two mappings, not two dates”

I ran three discriminators and concluded the pair could not be compared. The null test was sound (compare(A, A) → changed_frac 0.000000%) and the arithmetic was right. The verdict rested on a premise stated as if it were a law: “buildings do not vanish and asphalt does not become dirt.” In an area that was shelled they do.

why this one stings

It is the same shape as the soil-genesis priors this repo retired — reasonable-sounding world knowledge, wired into scoring code, wrong here. They cost 10,788 false findings and stayed invisible until someone read the worklist. taxonomy.RETIRED_PRIORS exists to remember that, and I made the same class of mistake in the same week, inside a document whose subject is that mistake.

The fix I proposed for it was worse than nothing: register 2.12 said s6_change should refuse a pair whose built-class retention is implausible. That gate would have refused this pair. A comparability check keyed on the built environment suppresses exactly the change it is most important to detect.

2 · Then I over-corrected, and a reviewer took that apart too

Handed the war, I asserted the label data rules out the segmenter. It does not. I put a fresh-context reviewer on the corrected claims with instructions to refute; it reproduced every arithmetic figure to the digit and then dismantled the reasoning by running it:

What actually settles it is the imagery — which the reviewer opened and I did not. The village is levelled. The honest formulation is “the label rasters are consistent with destruction and the source orthos confirm it”, never “the labels rule out the alternative”. The conclusion was right; the argument never reached it.

3 · A unit error running through every area figure

The same review found that loader.geotiff_gsd converts degrees to metres for a geographic CRS — that fix is in the code, with a comment explaining that face value would be catastrophic — but does not apply the Web-Mercator scale factor. So on any EPSG:3857 raster every area RT reports is inflated by 1/cos²(φ): 42.5% at this latitude. I documented that exact trap in segment.py's own docstring and then quoted pseudo-hectares as hectares in a damage assessment. Register 2.13; the fix is four lines and changes every area the repo has ever produced on 3857 input, so it is an owner call.

4 · And the smaller one from yesterday

I said HANDOFF (26,592 sinai findings) and S1-audit.md (41,669) disagreed. Re-ran it: 133,976 regions, 178 root causes, 26,592 findings — HANDOFF's figures exactly. S1-audit.md's table has two count columns, before and after the roll-up; 41,669 is the before-column. Nothing disagreed. The rebuild cost 5 min 06 s, not the ~24 min I used as my reason to skip it.

beyond

Future work, and what I would not do

Recommendations with the reasoning attached, so they can be argued with rather than accepted. The first two changed this morning.

Worth doing, in this order

  1. Build the damage product. The pieces exist: segmap segment makes the rasters, s6_change finds and categorises the transitions, the OSM layer has building footprints for this ground, and tilemap renders per-tile results. What is missing is the join — footprint-level status rather than pixel-level transition — and honest uncertainty on it. This is the highest-value unbuilt thing in the repo for this AOI, and none of it is research.
  2. Make assumptions in checks declare themselves. The failure this week was not a bug; it was a world-model premise (“buildings do not vanish”) inside a test, unlabelled. taxonomy.RETIRED_PRIORS already does this for scoring priors: name the assumption, name what would falsify it, keep the record when it is retired. Discriminators deserve the same treatment, and there is now a worked example to point at.
  3. Log the producer's model version into the raster. segmap segment already writes ST_MODEL and ST_MODEL_NATIVE_GSD, which is why this week's rasters are self-describing and the source orthos are not. Ask the product to stamp the same thing and S6's open question 2 becomes answerable from the file.
  4. Take the free outputs seriously. roads is a binary mask from the same forward pass and an independent opinion about the same ground as the OSM road layer — the one input S1's reference checks have no second source for. On this AOI it is also a damage signal: a road the model no longer sees is a road under rubble.
  5. Put a GPU behind segment. 35 CPU-minutes per ortho is tolerable once and obstructive as a habit, and there is an idle RTX 6000 in the machine. It needs onnxruntime-gpu and a CUDA runtime, not code — the provider fallback is already written.
  6. Then the region-unit problem. The sinai mosaic's largest region is one Rendzina component of 86.23 km² with 51,810 neighbours, while the median region is 26 m². It also bites here: 2,579 House → Clutter components collapse to 220 that matter, and the review measured 2.08 real buildings per component — walls shared, components merged. Largest and least contained item in the register, which is why it is last.

What I would not do

  • Do not add the comparability gate as I first specified it. Keyed on built-class retention it would have refused this pair, which is the one that matters. If a gate goes in, it keys on pipeline metadata, never on the scene.
  • Do not fix class_distance by adding a prior. It is the exact mistake that produced RETIRED_PRIORS, at a cost of 10,788 false findings. It needs a measured confusion matrix or a compatibility relation from the class owner — and note that on this AOI the taxonomy's own distances actively mislead: House → Clutter scores as maximally strange when it is the expected outcome.
  • Do not tune S4's constants before its output contract is decided — and reopen the question of which products, now that damage is on the table.
  • Do not spend an API key on S5 yet. The eval harness formats the headline scalar with :,g, so the model sees 203,551 where the stored truth is 203,550.80. Any model printing the exact figure cannot have got it from a tool — the harness awards full marks for the fabrication it exists to catch.
  • Do not read aza numbers as findings until its class mapping is confirmed. That AOI is also a conflict zone, so the same Clutter-as-rubble question applies there, on top of a mapping borrowed from another export.
